# 自研设备通信协议设计草案

状态：初步设计，尚未实现或冻结线上格式。本页整理协议方向和待决问题，不替代
[Device Contract](DEVICE_CONTRACT.md)、[现有 VOFA 协议](VOFA_PROTOCOL.md)或公共 Motor API。
活动阶段的交付范围与验收顺序由本地 Git 检查点保存。

## 目标与分层

以单电机控制器的设备访问、可靠请求响应、遥测和异常恢复展示嵌入式通信能力。
借鉴 Modbus 的简单地址化访问，以及 CANopen 的对象、过程数据和事件划分；不声明
标准 Modbus / CANopen 兼容，不实现其完整对象字典、NMT、动态 PDO、SYNC、LSS 或 CiA 402。

```text
Motor / Device API
        ↑
协议公共语义与事务处理
        ↑
UART Codec              CAN Codec（后续）
        ↑                      ↑
UART 字节传输             FDCAN / 收发器
```

单位、权限、错误、状态和命令含义统一，UART / CAN 可以使用不同帧头、负载布局、
遥测分组与分段策略。协议语义与编解码不依赖 HAL、FreeRTOS 或 PC 界面；业务请求
通过现有 Motor 边界提交，不直接操作 PWM、MOE、控制器积分或 Runtime 私有状态。

## 设备模型及最小操作

| 类别 | 用途 | 初步例子 |
| --- | --- | --- |
| Object | 持续存在的数据及参数 | 状态、故障、实际速度、母线、目标速度 |
| Command | 一次业务动作 | Start Velocity、Stop、Clear Fault |
| Telemetry | 一致性快照的周期发布 | 目标/实际速度、Id/Iq、母线、状态、有效位、采集时间 |
| Event | 状态变化或故障发生的通知 | Fault Occurred、State Changed |

请求先收敛为 READ、WRITE、COMMAND，配套关联响应、明确错误、TELEMETRY 和 EVENT。
每个 Object 后续逐项定义 ID、固定宽度类型、单位、权限、范围、适用状态和有效条件；
没有有效测量时必须表达无效，不能把初始化零值当作有效数据。

与现有 Motor 合同的适配原则：

- Start Velocity 自身携带完整速度目标；接收层不能分步写 mode / target 后启动。
- WRITE Target Speed 映射为完整 Update Velocity，仍受 RUN 状态、当前模式和范围限制；
  首版不额外建立 IDLE 预置目标语义，读取活动目标来自 Motor Snapshot。
- Current Limit 暂不承诺可写；开放前明确其与装配限值、软件撤销阈值的关系。
- Clear Fault 继续依照 Motor 实际恢复能力返回结果；协议不能把尚不可用的恢复实现为
  清寄存器或自动重启。Calibrate、持久参数等在有真实业务实现后再加入。
- 入队成功、业务 ACCEPTED、进入 RUN 和实际功率状态分别表示；入队不能冒充业务接受。

## 会话、事务与重试

请求序号用于关联响应和会话内重复检测。后续冻结会话建立/失效、序号宽度与回绕、
去重缓存容量和有效窗口；不承诺无限保存结果或跨复位恰好执行一次。

同一有效会话内，同序号且相同完整请求返回原结果或明确的处理中状态，不重复执行；
同序号不同内容应拒绝。缓存过期或越出接收窗口时，要能明确拒绝旧请求，不能把已经
执行过的旧 Start 当作新请求重新执行。设备复位、重新连接或会话失效后重新读取状态，
主机不自动恢复旧运动命令。线缆上的 UART 本身不能识别软件会话，需显式协议机制。

优先采用设置绝对目标，避免相对加减造成重复副作用；Stop 保持幂等。有效 Stop 在
请求队列拥塞时仍有确定的优先交接路径，并撤销更早的待执行运动意图。串口 Stop
不是独立硬件保护，CRC 错误或未完整验证的字节不能被猜测成任何运动/恢复命令。

遥测允许丢弃过时快照以限制积压，响应不能被遥测洪泛饿死。事件需明确顺序和溢出
可观测性；不能假定每个故障事件必然送达，锁存故障及当前状态始终可以主动读取。
断线后的运行处置、主机失联超时和事件可靠性仍需另行冻结。

## UART 字节流与异常恢复

帧内容初步包含 SOF、Version、Length、Sequence、消息类别、操作/对象标识、Payload
及 CRC；具体取值、位宽、CRC 参数、大小端与最大帧长尚未冻结。固定宽度整数与
binary32 必须显式序列化，不发送 C struct 原始内存。

解析器支持任意碎片、半帧和连续多帧输入；DMA、IDLE、HT、TC 只是字节到达通知，
不是协议帧边界。CRC 负责检错，解析状态机负责恢复；畸形帧不能派生有效业务请求。

| 输入异常 | 必须定义并验证的行为 |
| --- | --- |
| CRC / 版本 / 长度非法 | 有界拒绝并重新同步，后续完整好帧可被接收 |
| 半帧超时 | 丢弃未完成状态，不重放已接受请求 |
| 接收缓冲溢出或 UART 错误 | 标记流连续性丢失、使当前半帧失效并恢复同步 |
| 分隔符出现在负载或损坏候选中 | 明确长度、搜索与超时策略，避免长期吞掉后续好帧 |

DMA 到解析器之间只保留必要的有界缓冲。是否需要额外 Ring Buffer 由 DMA 覆盖边界、
消费速度和溢出检测决定；不强制复制多层缓冲。DMA producer / consumer 的唯一所有者、
回绕和 IDLE/HT/TC 重复通知必须明确，不能因为增加 RTOS 就丢失字节或重复交付。

设备自研协议遥测与 VOFA JustFloat 的帧格式不同，不直接混发。先保留既有 VOFA 兼容
模式和最小 PC 协议客户端；需要时在 PC 侧将自研遥测适配为 VOFA 可解析数据。转发和
安全模式切换细节待定，不开发 Qt 或通用插件框架。JustFloat 格式依据
[VOFA 官方说明](https://www.vofa.plus/docs/learning/dataengines/justfloat/)。

## FreeRTOS 集成边界

先让协议核心在 PC 离线测试、再在现有执行环境验证 UART 事务，随后迁移后台调度。
UART DMA 接收接口、解析器和业务分发以有界处理为目标，不提前搭建另一套通用调度框架。
串口错误恢复与任务迁移分别验收，避免一次改变所有执行条件。

20 kHz PWM、10 kHz 电流环和整数分频的 1 kHz 速度环继续由硬件同步驱动；控制 ISR
不调用 RTOS API，也不等待任务、队列或互斥锁。后台按通信处理、遥测发送等真实阻塞
和优先级需求决定任务数量，不按协议层数创建任务。后台只交接完整请求及读取一致快照。

Target 集成时核对内核/编译器移植兼容性、中断优先级、HAL tick / RTOS tick、任务与
中断栈、静态 RAM、FPU 上下文和最长临界区。DMA/通信 IRQ 如需调用 FromISR，遵守
[FreeRTOS Cortex-M 中断限制](https://freertos.org/Documentation/02-Kernel/03-Supported-devices/04-Demos/ARM-Cortex/RTOS-Cortex-M3-M4)。
有限缓冲、通信压力与遥测降载不能影响控制截止或故障关断。

## CAN 后续适配与冻结事项

CAN 实物联调不属于本轮 UART＋FreeRTOS 展示范围。后续 CAN ID 同时考虑消息类别、
节点身份、仲裁和硬件过滤；不在 CAN 帧里机械复制 UART 的 SOF / Length / 链路 CRC。
遥测可按过程数据预分组；大对象有真实需求后再设计分段传输。实际使用 Classical CAN
还是 CAN FD，需要核对收发器、其他节点及 bit timing，不能由外设名称直接推定。

正式实现前还需冻结：最小对象/命令表、Wire Protocol 版本与字段、CRC 完整参数、
会话及去重边界、超时/断线处置、队列容量与优先级、事件及遥测速率、VOFA 接入方式。
CAN ID、Node ID、分段和 RS485 硬件在对应需求出现时定义，不阻塞 UART 首次落地。
